# `cjsyntax` — the Cangjie lexer and parser

The Cangjie lexer and parser, on `ginkgo`: `tokenize(text)`, `parse(text)`, and `SyntaxKind`; `cjsyntax.ast`, the typed views of the tree. `SyntaxKind` and the views are generated from `syntax_kinds.toml` and `cangjie.ungram` beside the manifest.

The generator, `modules/syntax_codegen` (`executable`): `syntax_codegen modules/cjsyntax/syntax_kinds.toml` writes `src/syntax_kind.cj` and `src/ast/nodes.cj` there, through `cjfmt`. On `ftoml` and `stdxx` only, so a broken output never stops it being rebuilt; its tests take `cjsyntax` as a `[test-dependencies]` entry, and fail when what is checked in is not what it makes.

The trees and the grammar-agnostic parser machinery are `ginkgo`'s, in `modules/ginkgo/CLAUDE.md`; the grammar is here.

- **The grammar follows the compiler's parser** (`cangjie_compiler/src/Parse`), and its behaviour is the specification: when the two disagree, the compiler is right. The rules easy to get wrong: newlines end statements, but a binary operator other than `-` and `?` carries the expression on after one, and so does a `.`; `(`, `[`, `{` (a trailing lambda), `?`, `++`, `--` only continue an expression on the same line. `>` and `?` are always lexed alone, and the parser glues `>>`, `>=`, `>>=`, `??` from joint pieces. `a<b>(c)` is guessed by parsing type arguments and rewinding if they fail, plus the compiler's rule that among comma-separated expressions, arguments that could be expressions need a follower an expression can take (`f(a < b, c > d)` is two comparisons). Contextual keywords (`public`, `open`, …) are names wherever a name fits, remapped to `Ident`; builtin annotations (`@Deprecated`) are told from macro calls (`@M`) by name, through the contextual kind `BuiltinAnnotationName`. A string is lexed in pieces around its interpolations, so what is inside is parsed as code.
- **Errors go into the parse, never out of it** — structural checks the compiler's parser makes (a class in a class body, a function without a body outside a class, the order of `package` and `import`) included; semantic ones (modifier conflicts, annotation targets) are not, and belong to a later validation pass over the tree. An error is data, not words: `SyntaxError<K>` holds a `ParseError<K>` — `Expected(kind)` from `Parser.expect`, a `Message` for what the grammar only says — and the language words it (`cjsyntax.message`: `expected '}'`), since `ginkgo` knows no spelling of any kind.
- **`SyntaxKind` and the typed views are generated** (D10) by `syntax_codegen` from two files next to `cjsyntax`'s manifest. `syntax_kinds.toml` lists the tokens by section (trivia, punctuation the lexer cuts, punctuation the parser glues, other tokens, keywords with `contextual` ones marked, and the few nodes without a rule): each is one line, and every method of `SyntaxKind` (`ordinal`, `toString`, `isTrivia`, `isKeyword`, `isContextualKeyword`, `isPunctuation`, `fixedText`, `keyword`) and the lexer's `LEXED_PUNCTUATION` follow from it. `cangjie.ungram` is an ungrammar — a grammar of the tree's shape, not of the text — for every node, the node kinds come from it, and so does `cjsyntax.ast` (`src/ast/nodes.cj`): a struct per node — `cast`, `syntax`, an accessor per child and per token — and an enum per rule that only lists nodes (`Expr`, `Decl`, `Type`, `Pattern`, `Stmt`), its variants `As<Member>` or the rule's label (`DeclStmt:Decl`). A new token or node goes in those files, never in the output; regenerate with `cjpm build && target/release/bin/syntax_codegen modules/cjsyntax/syntax_kinds.toml` (it runs `cjfmt`). The views live in their own package because a struct `BinExpr` and the constructor `SyntaxKind.BinExpr` cannot share one; there the kinds are always written `SyntaxKind.X`. `SyntaxKind`'s constructors share `cjsyntax`'s namespace all the same (see the enum scoping note in `modules/lsp_codegen/CLAUDE.md`), so a kind must not be named like a type the package uses: `Resource` would shadow `std.core.Resource`, hence `ResourceDecl`; keywords end in `Kw` so `Int64Kw` does not shadow `Int64`.
- **An accessor finds a child by its position** among those that could be taken for it — `BinExpr.rhs` is the second `Expr` — and the generator works that out from the grammar, alternatives excluding each other included. Where the grammar cannot say (a child before it may be missing, as in `start:Expr? '..' end:Expr?`), it leaves the accessor out and prints a note; those are written by hand in `src/ast/node_ext.cj`, found by the tokens around them. A named group of tokens (`op:('+' | '-')`) is one accessor for any of them; a child named like a Cangjie keyword has to be labeled (`Type` alone is `ty`).
- **Tests** are snapshots in `parser_test.cj`: text against its tree as an S-expression (`sexp`, trivia left out) with the errors. The parser was checked against the compiler's test suite (`cangjie_test`, ~98k `.cj` files, with the compiler's own parser through `std.ast.parseProgram` as the oracle): every tree covered its text, and no file it reported an error in did the compiler's parser accept. Keep it that way — a false error in an editor is worse than a missed one. That harness is not in the repo; rebuild it (a walk over the files calling `parse`, and one calling `parseProgram`) when touching the grammar. The one checking trees against `cangjie.ungram` is: `ConformanceTest` in `syntax_codegen` holds every file of this repository to it exactly, trees with errors to holding nothing it does not allow, and a corpus too when `CJSYNTAX_CORPUS` names one (`CJSYNTAX_CORPUS=~/Projects/cangjie_test cjpm test '--filter=ConformanceTest.*'`) — a grammar change the ungrammar does not follow fails there, and so would the accessors.
