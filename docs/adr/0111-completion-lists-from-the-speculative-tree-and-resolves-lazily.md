# ADR-0111: Completion lists from the speculative tree, ranks by scope, and leaves the detail to a resolve

Status: proposed

## Context

- [#203](https://github.com/ide4cj/cjls/issues/203): after a `.`, the members of what is before it; at a name, what is in scope. The analysis answers each by name (`memberLookup`, `resolveBodyName`, `lookUp`, D50, D52), never all at once, and a body's scopes know which locals a declaration opens for what follows it, not an offset (D50): the file's own tree has no expression at a cursor on a line of its own.
- R1 lists what a scope holds (`ScopeDef`s, `process_all_names`) and what a type has (`iterate_method_candidates`), ranks each item by a relevance (`CompletionRelevance`: an exact name or type match, a local, an import needed) and leaves the match against what was typed to the client: "Filtering by identifier prefix/fuzzy match should be done higher in the stack". VS Code sorts by its own fuzzy score first and by `sortText` only among equals; an item's documentation it asks for in `completionItem/resolve`, which R1 answers one item at a time. R4 (`CompletionImpl.cpp`) filters on the server by a case-insensitive subsequence and sends no `isIncomplete`, so an item it dropped for a longer prefix is gone when the user deletes a letter.
- D81 holds the server to the queries a request executes, and a declaration's signature is a query of its own (`signatureTypes`, D54): a list of a few hundred names whose detail is rendered at once executes a few hundred queries, cold.
- cjc checks a member's modifiers at the use, not at the lookup (N80): `memberLookup` finds a `private` member of another type and inference reports it. A list is a use of each item.

## Decision

- **The position is read in the speculative tree** (D110): the file with `cjlsCompletionMarker` inserted at the cursor, parsed again around it. The marker's `NameRef` under a `MemberAccessExpr` is a dot completion, under a `RefExpr` a name in scope; anywhere else, nothing is completed. The types, the scopes of the file and the body it is in are the file's own: the receiver before the `.` is the same node in both trees (the text before the cursor is the same), found by range and kind, its expression by the source map; the locals in scope at the name are the speculative body's (`lowerBody`, `scopesOf` over it), each mapped to the file's own local by the node declaring it, for its type.
- **The members are every member the lookup finds** (`allMembers`): the names gathered level by level as `memberLookup` walks, then each looked up, so what hides what is D52's (an override hides what it overrides, an `extend` of another instance is none of them). After a value, those that are not static; after a type, the static ones and the constructors (cjc: `object cannot access static member`, `cannot access by type name`); after a package, what it exports as the file's package sees it (N76). Then **the use's check** (N80): a `private` member in the type or `extend` declaring it, a `protected` one in its package or a subtype, an `internal` or `public` one as its package is seen from the body's.
- **The names in scope are read from the scopes, not looked up each**: the speculative body's locals by scope, the declaration's and the type's type parameters, the members of the type around (the static ones alone in a static body), the package's `defMap`, the file's imports and the package's constructor imports (N73), each glob's exports, the prelude's last; and the keywords that start an expression. A name of a nearer scope hides one of a farther, but for functions, which overload: the rule of `resolveBodyName`, kept by the order the scopes are read in.
- **The server ranks, the client matches.** Each item carries a relevance, a number whose order alone means something: a local above the type's members above the package's declarations above the imports above the prelude above the keywords, a nearer scope above a farther. It goes out as `sortText`; the prefix is not matched on the server, which lists the whole position, and the list is complete (no `isIncomplete`), so the client filters on each keystroke without asking again. Matching what was typed, and against what type is expected, is the client's and a later step's.
- **The detail and the documentation are a resolve**: `completionDetail(db, fileId, offset, item)` renders one item as hover does (`Hovers.declItem` with no token), a member as a member of the value it was listed on; the list itself carries a label, a kind and what the item stands for (`CompletionSource`), and executes no query per item.
- **Fixtures** (D43): `checkCompletion` writes each item as `relevance label | kind | detail` under the name typed before the cursor, or the token before it, the detail resolved for the test alone.

## Consequences

- What #203 leaves open stays open: an import added with a name not imported (needs `packageIndex`, and a server-side match with `isIncomplete`), snippets for a call's arguments, the expected type in the ranking, named arguments as R4 offers them.
- A cursor outside a body, in a type's body between its members or at the top level, completes nothing yet: the marker parses as no `RefExpr` there.
- `Hovers` renders a declaration with no token (`?CjSyntaxToken`), the name being the declaration's first.
