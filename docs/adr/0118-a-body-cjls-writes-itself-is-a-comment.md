# ADR-0118: A body cjls writes in an expansion of its own is a comment naming the macro

Status: accepted, 2026-10-20
Amends ADR-0114: the `extend`s an outer macro copies have bodies of a comment, not empty ones

## Context

- cjls writes the expansions of std's `@Derive` and of `std.unittest.testmacro`'s macros itself, signatures only (#175). Each member's body was `{}`: cjsyntax needs a body of a function or a property in an `extend`, a `struct` or a `class` that is not abstract, and so does `parseDecl` of a workspace macro the `extend` is sent to (D114).
- `{}` reads, in `cjls/expandMacro` and the expanded file (D103), as a `hashCode` that does nothing, which only the leading comment disclaims.
- The analysis lowers no body of an expansion (`bodyWithSourceMap` lowers a `Source` file's alone): an empty body is typed by nothing and reported by nothing, so no body needs to be of the member's type. A `throw`, which would type for any return type, was considered and not taken: a body that could run is not what cjls wrote, and names an exception the user never chose.

## Decision

- **Every body cjls writes in an expansion of its own is a block of one comment, `// body generated by <macro>`**, the macro the call names (`stubBody`): `@Derive`, `@Test`, `@TestTemplate`, `@TestBuilder`, `@UnittestOption`. It is the one body of the `extend`s of `@Derive`, of `@Test`'s `asTestSuite` and registrations, and of `@UnittestOption`'s getters.
- The comment `cjls/expandMacro` and the expanded file start with stays: `signatures only, no bodies`.

## Consequences

- An outer workspace macro given the `extend`s (D114) copies bodies of a comment; one that reads them sees an empty block, as before.
- The block folds; whether the editor folds it on opening is the editor's own. The one-line `{ /* … */ }` was not chosen: on its own line the comment reads as a body left out, after the signature as noise.
- Once #176's step 4 runs std's macros in the macro server, cjc's own bodies replace these, and nothing here is read.
