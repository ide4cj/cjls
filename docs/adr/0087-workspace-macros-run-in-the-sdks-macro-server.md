# ADR-0087: The workspace's macros run in the SDK's LSPMacroServer

Status: accepted, 2026-10-20

## Context

- #176 (#47's third layer) left two hosts for running the workspace's macros out of process: the SDK's `tools/bin/LSPMacroServer`, R4's, or a host of our own built with the user's `cjpm` on first use, as R1 builds `proc-macro-srv`. Either way a `lib-macro_*` must be loaded by the runtime of the SDK that compiled it. The `Tokens` passed to a macro wrap a C++ `MacroCall` whose layout std.ast reads. And a token's kind is cjc's `TokenKind` number. All three belong to one cjc version.
- What the server is, read from cjc's sources (`cangjie_compiler` at dedb13fc). A live client written against the 1.3.0-alpha.20261002 binary confirmed it: `@Twice(1 + 2)` of a cjpm-built `lib-macro_*.so` came back expanded in 0.2–0.9 ms a call.
  - **Arguments** (`src/main-macrosrv.cpp:31-43`): `<readFd> <writeFd> <parallel 0|1> <$SDK/bin/cjc> <ppid>`. On Windows they are five, with inheritable `HANDLE`s in place of fds and no ppid. The runtime is found as `dirname(cjc)/../runtime/lib/<host>`. R4's `libcangjie-lsp` forks it with two pipes, `PR_SET_PDEATHSIG`, and its stdout redirected to stderr (`MacroEvaluationClient.cpp:492-569`). On Windows it uses `CreateProcess` and a kill-on-close job (`:571-699`).
  - **Wire**: a native `size_t` length, then a flatbuffer `MacroMsg`, whose schema `schema/MacroMsgFormat.fbs` the SDK does not ship. The message is a union `defLib | multiCalls | macroResult | exitTask`. A `MacroCall` carries:
    - the macro's name and position, the pair that keys its answer;
    - the input and attribute tokens and the call's span;
    - the names of the enclosing macro calls (`assertParentContext`) and the items their inner calls set (`getChildMessages`);
    - the symbol `macroCall_{a|c}_<Macro>_<pkg>`, the package and the library's path.

    A `MacroResult` returns the tokens, a status, the items `setItem` set, the parents asserted and the `diagReport`s. Nothing on the wire points into cjc's AST or `SourceManager`: a file id is opaque to the server.
  - **Tokens**: `kind` is cjc's `TokenKind` number (`include/cangjie/Lex/Tokens.inc`, experimental tokens included: `ILLEGAL` is 162 in this nightly). std.ast keeps the same numbering by hand (`getTokenKind(no: UInt16)`, public). Output tokens taken from `$input` keep their positions; those a `quote` made carry the call's position.
  - **Failures**:
    - An exception in a macro comes back as `ILLEGAL` with status FAIL, and the server lives on.
    - A symbol not found, or a library `dlopen` refuses, makes the server exit with code 0.
    - A field missing from a message crashes it: nothing is null-checked.
    - Nothing times out: a macro that loops hangs the server.
    - Diagnostics pile up across calls until an `exitTask(false)`.
    - In serial mode a `multiCalls` of several calls answers the last one alone. Parallel mode answers one call a message, has to be polled, and spins while it waits.
    - Libraries are never unloaded: after a rebuild, the same path still runs the old code.
  - **Loading**: a `lib-macro_*` has no `RUNPATH`, and std's libraries have no `SONAME`. Without `LD_LIBRARY_PATH` set to the SDK's `runtime/lib/<host>`, `dlopen` fails on `libcangjie-std-ast.so` and the server exits. cjpm puts a macro package at `target/release/<root>/lib-macro_<pkg>.so`. std's macros are at `runtime/lib/<host>/libcangjie-std-<pkg>.so`.
- `std.process` gives a child its stdio and no other descriptor.

## Decision

- **The host is the SDK's `LSPMacroServer`**, of the SDK `project_model` finds (D40), never one of our own. It ships with every SDK, built against that SDK's runtime, `MacroCall` and `TokenKind`, which a host built by us would have to match anyway. It needs no build on first use, and a macro that crashes takes the server down, not cjls. The price is a protocol of R4's that any nightly may change. So `MacroMsgFormat.fbs` is vendored from cjc's sources at the pinned nightly, as `CjoFormat.fbs` is (D37). Its views are generated by `fbs_codegen`, which gets a writer.
- **Started on POSIX through `/bin/sh`**: `exec "$0" "$@" 3<&0 4>&1 0</dev/null 1>&2` with the arguments `<LSPMacroServer> 3 4 0 <cjc> <cjls's pid>`. The protocol runs on fds 3 and 4. What a macro prints goes to stderr, never onto the protocol, as cjc arranges it. `LD_LIBRARY_PATH` is set to the SDK's `runtime/lib/<host>`. The server exits when cjls dies, by its own `ppid` check and by EOF.
- **One call a message, serial**: each `multiCalls` holds one `MacroCall` and is followed by `exitTask(false)`, so no diagnostic of one call reaches the next. Nested calls go innermost first: a call carries its parents' names and the items its inner calls set. Calls are not batched until a measurement on a quiet machine says the round trip matters (#176's cost question).
- **cjls turns its tokens into cjc's numbering** by a table generated from `Tokens.inc` at the pinned nightly. A test checks it against `std.ast.getTokenKind` of the SDK the tests run on, so a nightly that renumbers fails CI when `.cangjie-version` moves. The output is printed as text and parsed by cjsyntax as the file `ItemFile.Expansion(MacroCallId)` of #175. A token's position maps back to the input token it came from; a token a `quote` made maps to the call.
- **cjls guards the server**: an expansion past a deadline kills the server, and an exit at any time costs only the calls in flight. A new server starts for the next call. Its expansions are lost, and the last expansion that succeeded stands (#175's rule). A macro library rebuilt or removed restarts the server, since a library is never unloaded. A call whose library does not exist is never sent, because a symbol not found ends the server.
- **The macro packages are built by cjls**, in a target directory of its own (#176), never the user's `target`. Until that build ends, an item under a workspace macro is opaque (#175's step 3).

## Consequences

- An SDK whose numbering differs from the pinned nightly's sends wrong kinds, and the macros misread their input with no error. Expansion is on only when the SDK's `cjc --version` is the pinned one, or one whose table the generated table matches. Which of the two is open (#176).
- Windows has no way to pass the server two inheritable pipe handles through `std.process`. There it needs `CreateProcess` through FFI, or stays opaque (#86, #176).
- A protocol change in a nightly breaks expansion only, and shows when `.cangjie-version` moves: the vendored schema and the token table move with it, under the tests that compare them.
- std's macros may go to the same server from their `libcangjie-std-*.so`, replacing #175's own expansions under the same `MacroCallId` (#176's first comment).
