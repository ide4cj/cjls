# cjmcp как IDE для агента: задачи и протокол сравнения

Статус: согласованный объём — **24 зачётных запуска и 2 пилотных**.
Документ задаёт протокол; результаты эксперимента ещё не получены.
Сборку, задачи и пилоты при подготовке документа не запускали.

## 1. Что проверяем

Помогает ли cjmcp агенту писать и изменять Cangjie-код: понимать существующие
контракты, находить связанные места, использовать зависимости и завершать
изменение с меньшими затратами и меньшим числом ошибок.

Сравниваем две рабочие среды на одной модели:

| Режим | Доступ к Cangjie-коду | Остальные инструменты |
| --- | --- | --- |
| A — без cjmcp | Файловое чтение, `rg`, редактор, обычные скрипты | Git, сборка, разрешённые проверки |
| B — с cjmcp | `runPython`: анализ, навигация, чтение и редактирование по инструкциям сервера | Те же Git, сборка и проверки |

В A cjmcp и другие семантические IDE/LSP-инструменты физически отключены.
В B агент выбирает нужные запросы сам; заранее написанных решений или запросов
для конкретной задачи ему не выдаём. Текстовые операции внутри `runPython`
допустимы в пределах инструкций сервера; обход через shell для Cangjie запрещён.
Справка и рецепты cjmcp доступны только B, их чтение входит в стоимость запуска.
Общие проектные документы и языковые инструкции одинаковы в A и B.

Это сравнение **среды вместе с её рабочими инструкциями**, а не изолированной
скорости одного API. Выводы не распространяем автоматически на другие модели,
языки, проекты или произвольное сочетание shell и cjmcp.

## 2. Объём и порядок

Основные задачи: CJLS-1, STD-1, STDX-1, CJPM-1. Для каждой — три независимых
повтора A и три B: `4 × 3 × 2 = 24` запуска.

До них — два технических пилота на отдельной задаче CJLS-P: один A и один B.
CJLS-P: переименовать локальную переменную `hashes` в `nameHashes` внутри
`findReferences`, сохранив поведение; выполнить существующие focused-проверки
поиска ссылок и необходимую сборку. Это техническая задача, не измерение
пользы семантического анализа. Пилоты проверяют
выдачу инструментов, сбор логов, изоляцию, сборку и лимиты; в сравнение пользы
не входят. После пилотов разрешено исправить протокол, затем его нужно
зафиксировать. Все четыре запасные задачи остаются доступны.

Все запуски последовательные, без параллельных агентов и конкурирующих сборок.
Порядок задач в каждом повторе: cjls, stdlib, stdx, cjpm. Порядок режимов:

| Повтор | cjls | stdlib | stdx | cjpm |
| --- | --- | --- | --- | --- |
| 1 | A → B | B → A | A → B | B → A |
| 2 | B → A | A → B | B → A | A → B |
| 3 | A → B | B → A | A → B | B → A |

Каждый запуск получает новый диалог, исходное состояние репозитория и отдельные
артефакты. История пилотов, решения, оценки и транскрипты других запусков
недоступны агенту. Оператор не подсказывает решение. Необходимое вмешательство
фиксируется; такой запуск не считается автономно завершённым.

### Лимиты и конфигурация

Рабочий лимит — 90 минут на запуск, включая запросы IDE, сборки и проверки.
Дополнительный лимит — 120 000 входных и выходных токенов суммарно, включая
повторно переданный контекст; reasoning учитывается в выходных токенах, если
провайдер включает его туда. Не складывать его второй раз. Если runner не умеет
надёжно ограничивать токены, до пилота выбрать для всей серии только временной
лимит и записать это в manifest. Не применять разный учёт между режимами.

Точное имя и версию модели, reasoning effort, параметры семплирования и
runner фиксируем в manifest до пилота. Они одинаковы во всей зачётной серии.
Если доступен seed, используем одинаковый seed внутри пары A/B и разные между
повторами. Даже при одинаковом seed результаты не считаем детерминированными.
После фиксации серии менять модель или лимиты по результатам отдельных задач нельзя.

## 3. Исходное состояние и изоляция

Перед пилотами ответственный за запуск:

1. Фиксирует SHA всех четырёх проектов, compiler/runtime, cjdev, бинарника cjmcp,
   его рецептов и общих инструкций. Для stdlib фиксируется SHA `cangjie_runtime`,
   для cjpm — `cangjie_tools`. Записывает ОС, CPU, RAM, SDK и профиль сборки.
2. Проверяет сборку неизменённых проектов; для cjls — также предусмотренные
   проектом проверки. Эти подготовительные действия не являются агентными
   запусками и не входят в 26 запусков.
3. Проверяет доступность необходимых пакетов в cjmcp и сохраняет диагностику
   загрузки и макросов. Ошибки в посторонних пакетах не скрывает; оценивает,
   затрагивают ли они выбранную задачу.
4. Готовит одинаковый исходный SDK и прогретые сборочные зависимости. Каждый
   запуск получает отдельную копию или snapshot, включая кэши, scratch и dist.
   Результаты предыдущего запуска не используются как начальный кэш следующего.
5. Фиксирует точные команды сборки и проверок, cwd, env и список допустимых
   файлов/репозиториев для записи. Зависимости заранее доступны локально;
   поиск готовых решений в сети во время запуска выключен в обоих режимах.

Git worktree создаются только в `<project-root>/.codex/worktrees/`.
Для cjdev нужна проверенная привязка изолированных исходников к branch set и
его собственным scratch/dist; нельзя предполагать, что произвольный вложенный
worktree автоматически распознаётся cjdev. Эту привязку готовит оператор до
таймера, не агент во время задачи. Нельзя менять общий SDK других запусков.

В B каждый запуск начинает с нового процесса cjmcp и пустого workspace-кэша;
отсчёт начинается до запуска процесса. Время старта и загрузки проекта входит
в полную задержку и отдельно записывается, если доступно. Кэши ОС специально
не сбрасываем: одинаковая подготовка и чередование A/B уменьшают перекос.
Измерение повторно используемой «тёплой IDE» оставляем отдельным будущим опытом.

Для CJLS-1 cjmcp работает из заранее собранного неизменяемого артефакта.
Изменения исследуемого cjls не пересобирают работающий инструмент посреди запуска.
В каждом вызове B явно передаёт корень рабочего дерева; root/sessionId/revision
сохраняются в логе. После записи кода анализ проверяется на новой ревизии.

## 4. Основные задачи

Карточки ниже задают поведение, а не алгоритм решения. Оба режима получают
одинаковую карточку и исходные точки. Гипотезы о пользе IDE и замечания оценщика
не включаются в prompt исполнителя.

### CJLS-1 — структурированный результат поиска ссылок

**Исходные точки:** `modules/loupe/src/references.cj`,
`modules/cjls/src/handlers/references.cj`; API `findReferences`, `handleReferences`.

**Задание:** заменить `Array<Reference>` результата `findReferences` на тип,
различающий позицию без разрешённого символа и разрешённый символ с массивом
ссылок. Конкретную форму типа выбрать по соглашениям проекта. Обновить всех
потребителей, включая MCP-обвязки и их контрактную документацию.
Внешнее поведение LSP сохранить. Новый признак не должен обещать полноту поиска:
разрешённый символ не означает отсутствие неоднозначных или пропущенных ссылок.

**Ожидаемые случаи:** пробел, неизвестное имя, объявление, использование,
импортный псевдоним; существующая фильтрация объявлений в LSP. Добавить тесты,
проверяющие новый контракт и сохранение поведения обработчика. Не менять
алгоритм разрешения имён ради удобства новой формы результата.

**Проверка:** focused-тесты loupe, затронутых обработчиков и MCP; далее обязательные
проверки по области изменения из `docs/development.md`. Макрообвязки проверяются
сборкой использующего их пакета. Точный набор команд фиксируется при подготовке.

**Гипотеза:** cjmcp уменьшает пропуски потребителей контракта и время навигации
между API, обвязками, типами и тестами.

### STD-1 — вставка ArrayList в самого себя

**Исходная точка:** `stdlib/libs/std/collection/array_list.cj` в `cangjie_runtime`;
перегрузки `add(all:)` и `add(all:, at:)`.

**Задание:** обеспечить вставку исходного содержимого списка при передаче его
самого, в том числе через переменную типа `Collection<T>`. Например, список
`[1, 2, 3]` после вставки себя в позицию 1 должен содержать
`[1, 1, 2, 3, 2, 3]`. При добавлении в конец — `[1, 2, 3, 1, 2, 3]`.

**Ожидаемые случаи:** начало, середина, конец; достаточная ёмкость и рост
буфера; пустой список; источник через базовый интерфейс; обычная другая
коллекция. Сохранить проверки индексов и существующие правила инвалидирования
итераторов. Не вводить обязательное копирование обычного независимого источника
без объяснения необходимости.

**Статус исходной проблемы:** подозрение по порядку изменения буфера и чтения
источника, не воспроизведённый дефект. До фиксации серии проверить актуальность
по исходникам выбранного SHA. Если контракт уже выполнен, заранее заменить
задачу на STD-R в обоих режимах; не создавать искусственный баг.

**Проверка:** сборка stdlib и ревью путей исполнения для перечисленных случаев;
тесты и исполняемые пробы не обязательны и в эту серию не включаются.

**Гипотеза:** помощь при работе с перегрузками, обобщениями и внутренними
зависимостями. Задача также проверяет границу пользы IDE: алгоритмическое
рассуждение о перекрытии буферов инструмент не заменяет.

### STDX-1 — ArrayList как LogValue

**Исходные точки:** `src/stdx/log/log_value.cj`, `log_writer.cj` в `cangjie_stdx`.

**Задание:** добавить `LogValue` для `ArrayList<T>` при `T <: LogValue`.
Вынести общую запись последовательности для `Array<T>` и `ArrayList<T>` во
внутренний помощник. Сохранить публичные контракты существующих реализаций.
Записывать массив значений в порядке итерации, без промежуточного преобразования
в строку и без обязательного `toArray()`.

**Ожидаемые случаи:** пустой список, вложенные списки, `Option<T>`, пользовательский
`LogValue`; сбалансированные начало/конец массива при успешной записи, прежняя
передача ошибки writer’а без её подавления. Проверить совместимость с имеющимися
конкретными writer’ами по исходникам.

**Проверка:** сборка stdx и ревью; добавление и запуск тестов не требуются.

**Гипотеза:** навигация по реализациям интерфейса и API stdlib, понимание
ограничений типов и правильное повторное использование существующей записи.

### CJPM-1 — окружение программы через run --env

**Исходные точки:** `cjpm/src/command/run.cj`, `cjpm/src/implement/run.cj`
в `cangjie_tools`; `RunConfig`, `EnvironmentBuilder`, `startRun`.

**Задание:** добавить повторяемую опцию:

```text
cjpm run --env MODE=test --env TOKEN=a=b -- аргумент_программы
```

**Контракт:**

- Разделение по первому `=`; отсутствие `=` и пустое имя — ошибка до сборки.
  Пустое значение допустимо. Повтор имени: последнее значение побеждает.
- CLI перекрывает значение из окружения и конфигурации запуска. Для переменной
  поиска библиотек обязательные пути cjpm добавляются перед этим значением
  существующим механизмом, чтобы сохранить возможность запуска программы.
- Переопределения действуют только на запускаемую программу, не на сборку,
  build-script или родительский процесс.
- Опция работает с `--skip-build`. После разделителя `--` она является обычным
  аргументом программы. Без неё поведение остаётся прежним.
- Справка описывает синтаксис, повторения, приоритет и область действия.

**Проверка:** сборка cjpm и ревью цепочки от парсинга до окружения дочернего
процесса. Интеграционные тесты и запуск программы не требуются.

**Гипотеза:** меньше пропусков при сквозном изменении и меньше дублирования
существующего механизма работы с окружением.

## 5. Запасные задачи

Замена выбирается **до** зачётной серии по актуальности задачи или готовности
окружения. Ошибки агента или ограничения cjmcp, обнаруженные в зачётном запуске,
не являются основанием заменить задачу задним числом. Все повторы и оба режима
для выбранной задачи выполняются от одного исходного состояния.

### CJLS-R — управление включением объявлений в loupe

Добавить в поиск ссылок параметр `includeDeclarations` с прежним поведением
по умолчанию. LSP передаёт `ReferenceContext.includeDeclaration`; дублирующую
фильтрацию из обработчика убрать. Обновить обвязки, сохранить классификацию
импортного псевдонима и существующее различие между LSP `null` и пустым массивом.
Добавить focused-тесты и выполнить проверки cjls.

### STD-R — валидация диапазона ArrayList.remove

Уточнить контракт `remove(range: Range<Int64>)`: сначала проверять допустимость
границ, затем применять правило пустого или обратного диапазона. Недопустимые
границы вызывают `IndexOutOfBoundsException` и не меняют список; допустимые
пустые/обратные диапазоны ничего не меняют. Шаг, отличный от 1, по-прежнему
вызывает `IllegalArgumentException`. Для закрытого конца учитывать включённый
элемент без переполнения при крайнем значении Int64; пропущенные границы
нормализовать к началу/концу списка. Согласовать с одиночным `remove(at:)`
и обновить документацию. Это намеренное уточнение поведения, не заявление
о доказанном баге. Проверка — сборка и ревью, без тестов.

### STDX-R — множества как LogValue

Добавить `LogValue` для `HashSet<T>` и `TreeSet<T>` при подходящих ограничениях
типов, используя общий внутренний помощник записи последовательности также
для существующего массива. Сохранить порядок итерации `TreeSet`; не обещать
сортировку `HashSet`. Учесть пустые множества и пользовательский `LogValue`.
Проверка — сборка и ревью. Начинать с базового SHA, без результата STDX-1.

### CJPM-R — план запуска без исполнения

Добавить `cjpm run --dry-run`: разрешить проект, пути, аргументы и окружение,
но не запускать сборку, build-script или программу и не менять файлы проекта.
Отсутствие ещё не собранного executable допустимо. Вывести один JSON-объект:
`executable` (абсолютный путь), `args` (массив строк), `cwd` (абсолютный путь),
`envOverrides` (только добавленные/изменённые переменные), `wouldBuild` (Bool).
Остальное окружение не раскрывать; диагностика идёт в stderr, stdout содержит
только JSON. Сохранить обычный запуск, обработку `--` и `--skip-build`.
При невозможности разрешить путь без сборки явно завершиться ошибкой, не
выдавать приблизительный план. Проверка — сборка и ревью, без тестов.

## 6. Сборка и пределы проверки

Команды ниже проверены по локальному checkout FilaCo/cjdev,
SHA `4fb6b06014c61a95755d6417f9ce22471a54c693`,
[default_manifest.toml](https://github.com/FilaCo/cjdev/blob/4fb6b06014c61a95755d6417f9ce22471a54c693/src/cjdev/infra/data/default_manifest.toml).
Это шаблоны argv; `{profile}`, `{jobs}`, `{dist}` заменяет оператор конкретными
значениями при подготовке manifest, не передаёт их буквально shell.

| Проект | cwd относительно репозитория | Команда |
| --- | --- | --- |
| stdlib | `cangjie_runtime/stdlib` | `python3 build.py build -t {profile} -j {jobs} --target-lib {dist}` |
| stdx | `cangjie_stdx` | `python3 build.py build -t {profile} --jobs {jobs}` |
| cjpm | `cangjie_tools/cjpm` | `python3 build/build.py build -t {profile}` |

cwd в таблице содержит имя репозитория для различения проектов. Применять
команду нужно внутри указанного каталога, в окружении изолированного branch set.
`CANGJIE_HOME`, `CANGJIE_STDX_PATH`, PATH и пути runtime-библиотек берутся из
cjdev; одной команды Python без этого окружения недостаточно.
Зависимости: stdlib требует compiler/runtime, stdx также stdlib, cjpm также stdx.
Машинные `extra_args` и эффективный manifest cjdev сохраняются вместе с запуском.

Допустима обёртка `cjdev build stdlib`, `cjdev build stdx` или `cjdev build cjpm`
в корректном branch set; она также обрабатывает зависимости и установку.
Выбранный способ фиксируется до пилота и одинаков для A/B. Различие `-j` для
stdlib и `--jobs` для stdx существенно. Scratch-каталоги берутся из manifest:
нельзя удалять каждый каталог с именем `build`, часть из них содержит исходники.

Для сторонних проектов не требуем писать или запускать тесты и исполняемые
пробы. Перечни случаев в карточках — обязательства реализации и пункты ревью,
а не обещание динамической проверки. Сборка подтверждает собираемость;
поведенческая корректность остаётся подтверждённой только ревью. В итогах
не объединяем её с более сильной проверкой cjls под одним словом «прошло».

## 7. Одинаковый prompt исполнителя

Оператор подставляет карточку, корень, лимиты и подготовленные команды:

```text
Выполни задачу <TASK_ID> в <ROOT> от зафиксированного исходного состояния.
<Карточка: задание, исходные точки, контракт и разрешённые проверки.>
Следуй общим инструкциям проекта и инструкциям доступных инструментов.
```

## 8. Что сохраняем и как оцениваем

Для запуска сохраняем `manifest.json`, исходный prompt, полную трассу вызовов,
usage провайдера, stdout/stderr и exit code сборок, итоговый diff, финальный
ответ агента и независимое `review.md`. Метаданные включают task/mode/repeat,
SHA всех компонентов, время начала/окончания, лимит, причину остановки,
SDK/env без секретов, состояние кэшей и вмешательства оператора.
Для cjmcp дополнительно — диагностику загрузки/макросов, ошибки запросов,
root/session/revision. Отсутствующие метрики обозначаем `null`, не нулём.

### Корректность отдельно от стоимости

Ревьюер получает обезличенный diff и карточку, без режима, времени и затрат.
Для каждого требования ставит `выполнено`, `нарушено` или `не доказано`,
ссылаясь на конкретный код/лог. Затем получает результаты проверок и отдельно
фиксирует их силу: сборка, тесты cjls, только статическое ревью поведения.
Оцениваются также лишние изменения, публичные контракты, документация и
необоснованные заявления финального ответа. Идентичность эталонному diff не нужна.

Итоговые категории:

- **Принято по доступным проверкам:** контракт выполнен по ревью, обязательные
  проверки успешны, существенных незакрытых замечаний нет. Для внешних проектов
  явно указать: поведение не проверено исполнением.
- **Частично:** полезное изменение есть, но нарушены или не доказаны требования.
- **Не завершено:** нет пригодного решения, исчерпан лимит или осталась
  вызванная изменением ошибка сборки/проверок.
- **Инфраструктурно недействителен:** внешняя причина, не связанная с решением,
  сделала запуск несопоставимым; исходный лог сохраняется.

Сбой cjmcp на допустимом запросе — наблюдение о надёжности режима B, а не
автоматическое основание исключить запуск. Сбой машины или недоступность
провайдера может требовать повторения всей пары A/B; такие дополнительные
попытки явно перечисляются сверх запланированных 26, не выбирается лучший результат.

### Затраты и польза IDE

Собираем полное wall time, время команд сборки/проверок и, если трасса позволяет,
время старта/запросов cjmcp. Не называем остаток «временем мышления»: в нём
смешаны задержки провайдера, чтение, запись и оркестрация.
Сохраняем входные, кэшированные входные, выходные и reasoning-токены без
двойного счёта; денежную стоимость считаем по зафиксированному тарифу и usage.
Отдельно считаем количество сборок, исправлений после ошибок компилятора,
неуспешных обращений к инструментам и вмешательств оператора.

По трассе отмечаем конкретные эпизоды: найденный потребитель контракта,
выбранная перегрузка, обнаруженная реализация интерфейса, прочитанный API
зависимости, проверенная связь после правки. Число вызовов само по себе не
доказывает пользу. Для больших Python-запросов учитываем выданные агенту токены,
а не только количество вызовов. CPU/RAM инструмента можно добавить отдельными
полями, если runner измеряет их надёжно в обоих режимах.

## 9. Итоговый отчёт

Публикуем все 24 результата, не только лучшие. По каждой задаче — число
принятых решений из трёх, медиану и диапазон времени/токенов/стоимости,
ошибки и ограничения проверки. Сначала показываем корректность, затем цену.
Сравнение стоимости принятых решений делаем только при наличии принятых
решений в обоих режимах; не смешиваем быстрый провал с успешным завершением.
Рядом приводим затраты всех попыток, чтобы не скрыть стоимость неудач.

Различия представляем по задачам и по парным повторам, без заявления
статистической значимости на трёх повторах. Для каждого вывода добавляем
эпизоды трассы, объясняющие, где IDE помогла, не помогла или мешала.
Если B дороже или менее надёжен на задаче, это такой же результат эксперимента.
